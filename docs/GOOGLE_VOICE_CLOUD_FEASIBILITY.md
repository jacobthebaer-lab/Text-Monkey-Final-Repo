# Google Voice cloud feasibility research

Research date: October 3, 2026. This records the research before implementation. The user subsequently authorized building the isolated experiment; see [cloud setup and validation](CLOUD_GOOGLE_VOICE.md) for the implementation. No real Google Voice delivery has been verified.

## Decision so far

Text Monkey can plausibly operate while the coordinator's computer is off. The evidence does **not** establish a fully browserless, free, Cloudflare-only Google Voice transport for personal accounts. The maintained Google Voice bridge currently documents a headless Electron requirement for outgoing personal-account messages. That browser engine can run in the cloud.

The experiment is isolated in branch `codex/google-voice-cloud-research`, initially based on integration commit `7939651` and advanced to `edc40f2` before implementation. The later documentation-only integration commit `e974a38` was also incorporated. The original checkout and its uncommitted work have not been edited by this work.

## Google Voice evidence

- [mautrix/gvoice](https://github.com/mautrix/gvoice) is a newer maintained implementation than the archived Beeper example. Its [changelog](https://github.com/mautrix/gvoice/blob/main/CHANGELOG.md) includes a May 2026 incoming-data parsing fix.
- [Setup documentation](https://docs.mau.fi/bridges/go/setup.html?bridge=gvoice) requires headless Electron for sending from non-Workspace accounts.
- The [HTTP client](https://github.com/mautrix/gvoice/blob/main/pkg/libgv/client.go) implements account lookup, inbox/thread reads and SMS sending. The [incoming channel](https://github.com/mautrix/gvoice/blob/main/pkg/libgv/channel.go) implements HTTP long polling. Incoming reading does not inherently require browser UI automation.
- [Outgoing handling](https://github.com/mautrix/gvoice/blob/main/pkg/connector/handlematrix.go) uses a tracking signature generated by [Electron](https://github.com/mautrix/gvoice/blob/main/pkg/connector/electron.go). An unsigned fallback exists in code but is not proof that personal-account sends succeed.
- [Authentication](https://docs.mau.fi/bridges/go/gvoice/authentication.html) uses a single-account Google session, not a supported Google Voice OAuth integration. Cookie rotation exists; indefinite unattended authentication is not established. Session expiry must pause transport and request reconnection.
- [PR 23](https://github.com/mautrix/gvoice/pull/23) reports an Electron initialization issue after Google's landing-page redirect changed. [PR 24](https://github.com/mautrix/gvoice/pull/24) reports initiating new one-to-one conversations. Both require review and live validation; an open PR is not verified functionality in our app.

The selected account's signup UI requires an existing US mobile number and government-issued ID verification before messaging is enabled. Area-code availability is dynamic. No number has been fully claimed by this research.

Linking a mobile for initial verification need not mean permanent call forwarding. [Google's instructions](https://support.google.com/voice/answer/165221?co=GENIE.Platform%3DDesktop&hl=en) describe turning forwarding off and removing linked numbers. Standalone use after setup is separate from skipping signup verification.

## Cloudflare evidence and existing app

- [Scheduled Workers](https://developers.cloudflare.com/workers/configuration/cron-triggers/) run without an open admin page. A proposed minute poll uses 1,440 invocations/day.
- [Free Workers limits](https://developers.cloudflare.com/workers/platform/limits/) include 100,000 requests/day and 10 ms CPU per request or cron invocation. Network waits do not consume CPU, but authentication, parsing and application logic do. Free operation needs actual CPU measurements.
- [Browser Run pricing](https://developers.cloudflare.com/browser-run/pricing/) allows 10 browser minutes/day on Free. An on-demand browser could be a small-demo experiment, but its Google compatibility and daily usage have not been tested. It cannot be presented as free continuous browser hosting.
- [Python FastAPI](https://developers.cloudflare.com/workers/languages/python/packages/fastapi/) and [synchronous Postgres/SQLAlchemy through Hyperdrive](https://developers.cloudflare.com/hyperdrive/examples/python-workers/) are supported in current docs. This is a migration possibility, not confirmation that our exact dependency versions run unchanged.
- `web/texty/worker.js` currently forwards API requests to a separate backend. The public Pages demo is static and synthetic, as documented in `docs/CLOUDFLARE_DEMO.md`.
- `app/main.py` runs a threaded 30-second APScheduler. [Workers Python restrictions](https://developers.cloudflare.com/workers/languages/python/stdlib/) mean it needs platform scheduling; local SQLite/files cannot be durable cloud state.
- `app/web/texty.py` enforces confirmed Supabase identities and an admin email allowlist. A distinct superadmin role is not currently implemented. A future transport setup screen requires server-enforced superadmin permission; the login manages transport but must not power its background execution.

## Best candidate for free ongoing hosting

Keep the Cloudflare admin front end and run the Python backend plus Google Voice connector and headless Electron on an Oracle Always Free Ubuntu ARM VM. This preserves the existing runtime model while moving execution off the Mac. It is a candidate to test, not verified delivery or guaranteed uninterrupted free hosting.

- [Current Oracle allocation](https://docs.oracle.com/en-us/iaas/Content/FreeTier/freetier_topic-Always_Free_Resources.htm): 2 ARM OCPUs and 12 GB RAM total, 200 GB combined boot/block storage and 10 TB monthly outbound data. Free compute must be in the home region. Capacity can be unavailable, and Oracle can reclaim idle instances after seven days under its documented utilization criteria.
- [Signup requirements](https://www.oracle.com/cloud/free/faq/) include card verification. Use only Always Free resources and do not upgrade or purchase resources as part of this research.
- [Electron](https://github.com/electron/electron/blob/main/docs/tutorial/installation.md) and the [bridge installation instructions](https://docs.mau.fi/bridges/go/setup.html?bridge=gvoice) offer Linux ARM64 builds. Exact runtime compatibility still needs a test.
- The existing Cloudflare proxy can connect to that backend. [Cloudflare Tunnel](https://developers.cloudflare.com/tunnel/) is another candidate for an outbound connection, subject to setup and validation.
- Cloudflare-only on-demand browser signing would require adapting Electron-specific code to Cloudflare Chromium. Its 10-minute daily free allowance is a demo limit, not continuous browser hosting.
- A normal Google Compute free-tier VM with public IPv4 fails the strict $0 requirement: [IPv4 pricing](https://cloud.google.com/vpc/network-pricing#ipaddress) is $0.005/hour with one free hour/month. An IPv6-only alternative is unverified for this app's dependencies.

Gloo AI and existing database allowances must be verified separately before calling the complete system free. The superadmin would manage setup and reconnection; routine processing must continue without the admin page open.

## Required proof before integration

1. Finish the user's selected Google Voice account setup without forwarding calls to the personal mobile afterward.
2. Establish an authorized, isolated Google session and make a minimal read-only account query. Do not start a full bridge that automatically imports contacts or conversations for this check.
3. Test the cloud outgoing-signature path. Actual send/reply and carrier delivery checks require a named consenting test recipient and exact test scope; none have been run.
4. Measure hosting CPU, browser time and durable-state usage under the free limits. Verify Gloo's allowance separately.
5. Verify reconnection, duplicate-job prevention, consent, eligibility, quiet hours, scheduling and review holds.
6. Complete a true end-to-end cloud test with local backend, local connector and coordinator computer off.
7. Only after these checks, review a feature-branch PR targeting `codex/complete-text-monkey`. Preserve the existing public preview and connected application until integration is approved.

Synthetic previews, queued acknowledgments, source-code claims and a successful sign-in must not be described as actual message delivery.
