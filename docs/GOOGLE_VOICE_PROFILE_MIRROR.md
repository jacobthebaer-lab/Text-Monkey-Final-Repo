# Scoped Google signup profile mirror

SQLite remains the operational database. The optional publisher independently mirrors one reviewed signup into the intended Supabase `texty` schema; it does not send texts, schedule events or grant qualifications. Existing Mac publication and its private scope remain unchanged.

Before activation, record a read-only baseline for the exact recipient with `tools/read_profile_baseline.py --scope-file PRIVATE_SCOPE --target-env-file PRIVATE_TARGET --output NEW_PRIVATE_RECEIPT`. Preserve and report any existing profile, preferences and qualifications. Never delete a row to make a wrong-name test appear empty.

Create a **new** private scope JSON containing `transport: "google_voice"`, exactly one synthetic/example `phones` entry replaced privately by the intended tester, the intended `project_ref`, exact `session_id`, expected `sender_fingerprint`, `expected_name: {first_name: ..., last_name: ...}`, and reviewed optional `role_map`. Obtain session and sender binding from the actual registration, not a fabricated fixture. Keep the scope and a separate target env containing `PROFILE_SYNC_DATABASE_URL` private, mode 0600 and readable by container UID 1000. The DSN must match this project's Supabase host/pooler identity; only the publisher receives it.

After source review, use the **existing Compose project**, private env and volumes with `compose.yaml`, the existing HTTPS overlay and `compose.profiles.yaml`. Supply explicit absolute `GOOGLE_PROFILE_SCOPE_FILE` and `GOOGLE_PROFILE_TARGET_ENV_FILE` paths; set `GOOGLE_VOICE_PROFILE_SYNC_ENABLED=true` only in the reviewed backend configuration. Add `--profile profiles` and explicitly start `backend profile-publisher` through the runtime owner. Leave `PROFILE_SYNC_ENABLED=false`. Default setup does not start this publisher or enable this flag.

Both capture and every publication revalidate actual inbound receipt, original submitted invitation, sender/session binding, both expected name parts and current consent. Altered/revoked evidence holds publication. STOP takes precedence and can update only an existing cloud profile. Names alone publish an inactive identity while preferences remain pending. Incomplete availability cannot be marked complete. Approved role qualifications and unrelated people/cloud fields are preserved; interested roles are only preferences. Qualification verification and scheduling/reminder authorization require their own existing reviewed workflows.

Acceptance requires private readback after wrong-name input (no new profile/outbox), correct-name input (one verified identity), and complete preferences (exact mapped data). Compare against baseline, confirm existing qualifications/privileges remain intact and repeat publication to prove idempotence. Synthetic checks do not establish live Supabase access or delivery.
